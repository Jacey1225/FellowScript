# Intake Brief — Note reply-thread layout options (Note detail screen, iOS)

Task: `20260828-note-reply-layout-options`

## Request (verbatim)

> there's one last thing that I forgot needed to be added into the notes feature. When a user clicks to view a note, some of them will have replies attached. Can you run the /design pipeline to come up with 3 different layouts for this new integration on the iOS, report back to me on them, and I will choose which to go through on the /build pipeline? ## Deliverable

Each option should place/present the reply thread differently (the user explicitly invited placement variety: "the replies showing up in different areas as well" — e.g. inline thread below the note body, a slide-up/modal sheet, a side rail, a collapsed count-badge that expands, or another candidate the synthesis/spec stage proposes). This is a **multi-option comparison deliverable**, not a single locked spec — the user will pick one favorite to carry into a separate, later `/build` pass, matching the established pattern from `.claude/design/20260828-continue-button-circle-icon-options/` in this same repo (read directly as a structural precedent for scoping a multi-option comparison; unrelated subject matter, same deliverable shape).

**Flag for downstream stages (synthesis, spec, generation):** `design-reference-synthesis-agent` and whichever spec agent follows should treat "produce exactly 3 distinct rendered layout options, not one locked design" as a first-class requirement, matching the `-continue-button-circle-icon-options` precedent's flagging pattern. `design-generation-agent` should expect to render three candidate screenshots/mockups, not a single asset.

## Desirables

- Three genuinely distinct **placements/mechanisms** for surfacing a note's replies from `NoteDetailView`, per the user's explicit invitation to vary "the replies showing up in different areas" — not three cosmetic skins of the same single mechanism.
- Every option must integrate into the *actual* current `NoteDetailView` structure (dark bloom background, Playfair serif title, hairline divider, serif note body, Close/Edit pill toolbar) — visual continuity with the app's established warm amber-on-dark, glass/gradient-pill, serif-body language is a hard constraint, not optional flourish.
- Each option needs a clear entry affordance (how a user with replies present becomes aware replies exist and how they open/reveal them) and, since this is a comparison of full concepts rather than one worked-through flow, a clear description of the open/expanded state.
- Reuse of existing pill-button visual language (`gradientPill`/`ghostPill` tokens: gold gradient fill + `#24170A` dark-brown content vs. ghost outline) for any new interactive affordance the options introduce, rather than inventing an unrelated new button style.
- Each reply, when rendered, should read as authored content distinct from the parent note — needs its own author identity (the model already carries `username` per reply, since a reply is itself an `FSNote`) and its own timestamp, at minimum.
- Should account for both the empty state (a note with zero replies — likely no visible affordance, or a muted "no replies yet" treatment) and the populated state (one or many replies) per option, since the request frames this as something that shows up conditionally ("some of them will have replies attached").
- Should account for the group-note context already present in this app (Personal vs. shared-group notes, per the list-view pill filter) — group notes are the context with an actually-wired reply-fetch endpoint today (see Gaps), so at least being aware of how a shared/group note's replies (potentially multiple distinct authors, a real social/community reading) might visually differ from any future personal-note reply use is worth a passing consideration, even if not a fully separate track.
- Realistic SwiftUI implementability grounded in the actual current `NoteDetailView` source (`NavigationStack` > `ScrollView`/`VStack` body, existing toolbar sheet pattern already used for `Edit`) — each option should be describable as a plausible extension of that real structure, not a hypothetical redesign, so whichever the user picks can go directly into a `/build` pass.
- A genuinely multi-option, comparison-oriented deliverable (three real rendered mockups/screenshots) rather than one finalized spec — the user picks a favorite afterward for a separate `/build` pass.

## Gaps

(Flagged forward for synthesis/spec to resolve or re-flag — not blocking this intake pass.)

- **This is not a fully greenfield data model, but it is also not fully wired end-to-end — worth flagging precisely.** A working `POST /notes/reply/{note_id}` endpoint, a working `GroupsManager.fetch_replies()` query, and a live `GET /community/{user_id}/{note_id}/{group_id}/replies` endpoint already exist (references 4-5), and the iOS `FSNote` model already has a decode-ready `replies: [FSNote]` field (reference 6) — but there is **no GET-replies endpoint for a personal/non-group note** (the only wired fetch route requires a `group_id` path segment), and `GET /notes/{user_id}` (personal note listing) hardcodes `"replies": []`. So a personal (non-group) note's replies cannot currently be fetched by the client at all, only a group note's can. This is a real backend gap the design pass should flag forward rather than silently assume is solved — it may constrain which of the 3 layout options are realistically buildable for personal notes in the very next `/build` pass without an accompanying small backend addition, or it may mean the initial `/build` pass scopes to group notes only. Not a `/design` pipeline blocker (design produces the visual/layout comparison regardless), but worth a visible callout in the style-brief/spec so the user's eventual `/build` choice isn't surprised by it.
- **Who may reply, and to which notes.** The existing `POST /reply/{note_id}` endpoint already answers this at the API level (owner, or anyone who can view the note — i.e. it's public, or the replier shares a group with it) — but the request itself doesn't say whether the *replies UI* should expose "write a reply" as part of this design pass's scope, or purely how to *display* already-existing replies. The request's own framing ("some of them will have replies attached... Can you run /design... for this new integration") reads as primarily about *displaying* replies; a reply-composition affordance (text field, submit) may be worth including in each option's affordance description for completeness, but should be treated as secondary to the three placement concepts themselves.
- **Exact number/length of sample replies to render per mockup** — not specified; synthesis/spec should choose a realistic small set (e.g., 2-3 short replies) consistent with the note-body content shown in reference 2, to make the layout differences legible without overloading the mockup.
- **No explicit dimensions/aspect ratio were given for the mockups themselves** (e.g., device frame, resolution) — reasonable to default to the same device framing as the supplied reference screenshots unless synthesis decides otherwise.
- **No explicit deadline** was given.
- **Platform is implicitly iOS/SwiftUI only** (matches the existing codebase, screenshots, and explicit "on the iOS" wording in the request) — no multi-platform ask.
- **Light/dark mode variant count** — likely moot; the app is forced dark per existing source comments in this same screen's precedent files (from the sibling `-continue-button-circle-icon-options` task's own investigation) — synthesis should confirm but this is not expected to be a real open question.
- **Whether any of the 3 options should also account for very long reply threads (many replies)** or is scoped to the common case of a handful — not addressed by the request; reasonable for synthesis/spec to pick a common-case scope (e.g., handles up to ~5-10 visibly, with an overflow/see-more treatment only if that's cheap to describe) rather than treating deep pagination as in-scope.

## Success criteria

- Three genuinely distinct reply-placement mechanisms are produced (not three color/icon variants of one mechanism), each as an actual rendered mockup/screenshot grounded in `NoteDetailView`'s real current structure — the user needs to visually compare real layouts, not read verbal descriptions.
- Each option clearly shows: the existing note-detail screen elements unchanged (Close/Edit toolbar, serif title, date, hairline divider, serif note body) plus its own distinct reply-thread placement and entry affordance, in both an empty-state-aware and populated-with-sample-replies state (or at minimum the populated state, with empty state described).
- Every option stays visually consistent with FellowScript's established warm amber-on-dark, gold-gradient-pill, serif-reading visual language shown in the reference screenshots — no option should read as an off-brand departure or introduce a visual system unrelated to the rest of the app.
- The backend/data-availability gap (personal notes currently have no wired GET-replies path, only group notes do) is surfaced explicitly in the style-brief/spec rather than silently assumed away, so the user's downstream `/build` choice isn't blindsided by needing a small backend addition.
- Each option is grounded in what's realistically buildable against the actual `NoteDetailView`/`FSNote` source (informed by references 4-7), so that whichever option the user picks can go directly into a follow-up `/build` pass without a redesign detour.
- The user can look at the finished set of three and clearly identify a favorite — the deliverable succeeds if it enables a confident choice among genuinely different placement concepts, not if it prematurely narrows to one answer.
- Downstream pipeline stages (synthesis, spec, generation) carry forward the "exactly 3 distinct options" requirement explicitly rather than collapsing this into a single-answer spec or single generated asset.
