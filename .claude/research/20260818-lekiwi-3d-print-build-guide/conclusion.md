# Conclusion: LeKiwi From-Scratch Build Walkthrough (3D-Printed Parts, Chapter-Mapped)

## Bottom line

The chapter-mapped build guide is sound and buildable as structured. LeKiwi's official print files, the print-vs-buy split, the five-phase assembly sequence, and the software/firmware setup all trace to primary sources and hold up under critique. The chapter mapping itself was never challenged and carries forward unchanged. Two real corrections came out of this round. The motor-ID pitfall (7/8/9 to rear/left-front/right-front) is not a Seeed-kit quirk as the brief worried — it is hardcoded in the official driver source and universal to every LeKiwi build on the standard stack; state it as a hard fact, not a caveat. The brief's claim that print/assembly friction is "thinly documented" with an implicit smooth-build impression is too strong — independent GitHub issues and merged PRs show real design-file friction (a mirrored camera-mount cutout, a motor-mount redesign for rigidity) that the original search missed. Three numbers stay unverified rather than confirmed: whether the arm's no-heat-set-insert design holds up in practice, whether the ~34-hour print time and ~2-hour assembly time are realistic, and whether real-world spend tracks the $482–499 reference BOM. None of these were contradicted — they were simply never independently checked, because the searches most likely to surface real builder complaints (forums, Reddit, video logs) never ran.

## Per-section findings

### 1. Official print files, location, printer requirements
Holds. The base/chassis files live in `SIGRobotics-UIUC/LeKiwi`'s `3DPrinting.md`; the arm files live in `TheRobotStudio/SO-ARM100`'s `STL/SO101`. Printer settings (PLA, 15% infill, 0.2mm layer height, ~34h total print time, supports only on the wheel hub) are vendor-documented and corroborated by the independent Seeed Studio wiki, with one cosmetic discrepancy (PLA vs. PLA+) never resolved as meaningful or incidental. The no-heat-set-insert design on the arm and the ~34h print-time figure are both unresolved for real-world accuracy — a targeted GitHub issue-tracker search for stripped threads and print-time complaints came back clean, but that search never reached the forums and Reddit threads where hobbyists actually post this kind of failure. Report both as vendor-sourced, not independently verified.

### 2. Print-vs-buy split and BOM
Holds as a structural claim, unresolved as a cost claim. The itemized $482 (12V) / $499 (5V) BOM, the printed-parts list, and the purchased-components list are all correctly sourced and complete. Whether real-world spend tracks that $482–499 figure is genuinely open — this is the weakest-executed check in the whole critique round, since two of four planned GitHub cost-search queries hit rate limits before completing. The one other independent data point (orobot.io's $450–550 estimate) is itself an estimate, not an itemized actual-spend account, so it doesn't confirm the baseline either. The separately-flagged four-way cost inconsistency ($482–499 / $660 / $770.47 / $450–550) remains unreconciled by design — the plan ruled that reconciliation out of scope — and should stay hedged wherever a single cost figure is cited.

### 3. Phased assembly sequence
Confirmed and strengthened. The official five-phase sequence (wheel modules, bottom plate/electronics, top plate/Pi/arm mount, final assembly/cable routing, camera mounting) is fastener-level and corroborated by the independent Seeed wiki at a coarser phase level. The one real reversal in this whole research task lives here: the brief's own hedge that the motor-ID pitfall might be a Seeed-specific kit-variant note is disproven by direct inspection of the official `lekiwi.py` driver source, which hardcodes `Motor(7)`/`Motor(8)`/`Motor(9)` to left-front/rear/right-front across every standard build. An independent, still-open GitHub issue confirms this is a recurring real builder pain point, not a one-off. The ~2-hour assembly-time estimate remains unresolved for the same reason as print time — vendor-sourced, no independent build log to check it against.

### 4–5. Software/firmware setup phase
Untested by critique, carries forward unchanged. No claim from this section was selected as a counter-evidence target, so nothing in this round confirmed or weakened the HF LeRobot install/calibration/teleoperation walkthrough or the Seeed-wiki-sourced software gotchas (USB permissions, the `lerobot-find-port` cable-disconnect requirement, macOS Input Monitoring, SSH disabled by default). Treat this content as it stood at the end of sourcing: primary-sourced, independently corroborated on the gotchas, but not separately stress-tested.

### 6. Known friction points and build risks
Split verdict, and the split is real rather than a hedge. On the brief's narrow, named failure-mode list — warping, tolerance mismatch, part breakage, heat-set-insert problems — nothing in the counter-evidence round touches any of them, so that list stands uncontradicted. On the brief's broader framing — "no independent account documenting physical friction," an implicit smooth-build impression resting on one experienced builder's account — that framing is disproven. A first-hand, dated GitHub issue documents a mirrored camera-mount cutout requiring a manual STL fix, and a maintainer-merged PR replaced the drive-motor mount specifically to fix a rigidity shortcoming. Both were sitting on the same repo the brief already cited and were simply missed by a web/vendor-focused search. How severe or representative that design-file friction is stays open — the camera-mount issue is scoped to an alternate camera outside the default BOM, and it's unclear whether a stock-BOM builder would ever hit it.

### Chapter mapping (research steps 4–5's core deliverable)
Not targeted by counter-evidence or critique — this is interpretive synthesis, not an empirical claim, so it was never in scope for the counter-evidence stage to contest. It carries forward from the brief exactly as written: wheel modules and drive-control software to Ch. 13 (wheeled mobile robots); arm sub-assembly to Ch. 2–3 (configuration space, rigid-body motions); electronics/Pi/arm mounting to Ch. 4 (forward kinematics); calibration to Ch. 11 primarily and Ch. 5 secondarily; software/firmware install and teleoperation architecture to Ch. 11; final integration and imitation-learning data collection to Ch. 9 and Ch. 12. The one self-flagged gap — no phase meaningfully exercises Ch. 8 dynamics, because the build uses position-controlled hobby servos with no runtime dynamics computation — was never resolved one way or the other and should be stated as a known limitation of the mapping, not smoothed over.

## Confidence

High confidence in everything structural: file locations, the printed-vs-purchased split, the five assembly phases, the software install/calibration sequence, and the chapter mapping as an interpretive framework. High confidence, upgraded this round, in the motor-ID mapping being universal rather than kit-specific — it's backed by the actual driver source code, about as strong as evidence gets for a software-configuration claim. Low confidence in three specific numbers: the no-heat-set-insert design's real-world durability, the ~34h print / ~2h assembly time estimates, and real-world spend versus the $482–499 baseline. Low-to-moderate confidence in "the physical build is smooth" as a general claim — downgraded this round by real, dated, non-vendor evidence of design-file friction, though nothing found rises to the severity of warping, breakage, or a heat-set failure.

What would overturn a finding: a forum, Reddit, or video build log surfacing stripped-thread or print-tolerance complaints would flip claim B from unresolved to false. An itemized real-spend account (including shipping, duties, reprints) landing meaningfully above $499 would confirm the brief's original worry about the reference BOM understating true cost; one landing at or below it would confirm the baseline instead. A second independent builder account reporting real physical-assembly friction would tip the "smooth build" question from split-verdict toward genuinely friction-prone. Evidence that the two inaccessible community-remix wheel-hub adapters exist because of a fit problem with the official design — rather than servo-brand preference — would add a new, previously unweighted risk to the printed-frame path specifically.

## Open questions

- Does print-specific failure data exist outside this round's search reach (Reddit, YouTube build logs, forum threads) that would change the smooth-build impression currently rebutted only by GitHub design-file issues, not physical-print failure reports?
- Is the $660 aggregator headline figure closer to the $770.47 Dynamixel variant, a mixed/regional-pricing Feetech build, or something else — left unreconciled by design, but the ambiguity should stay visible wherever a single LeKiwi cost figure is cited downstream.
- Do the two inaccessible community-remix files (Printables and Thingiverse OmniWheel-to-STS3215 adapters) indicate a genuine fit or tolerance issue with the official wheel-hub design, or just an alternative preference? Neither side could fetch them (HTTP 403, no working browser-automation tool this round).
- Is the PLA vs. PLA+ wording discrepancy between the official docs and the Seeed wiki meaningful for the load-bearing wheel-hub part, or purely incidental?
- Should the Ch. 8 dynamics gap in the chapter mapping get a thinner, caveated mapping to some part of BOM/part selection (e.g., motor torque sizing), or is "no phase maps cleanly" the honest final answer? This was flagged for critique to weigh in on and was never picked up as a counter-evidence target, so it stays open.
