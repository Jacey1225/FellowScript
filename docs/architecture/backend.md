# Backend

The backend is a **FastAPI + Postgres** application in `api/`. All code follows a strict three-layer flow:

```
routes/ (HTTP)  ──▶  backend/interactions/ (logic + DB)  ──▶  Postgres
   ▲                          │
   └── schemas/ (Pydantic) ───┘
```

---

## Entry Point — `main.py`

Registers all routers, configures CORS, and handles the three authentication routes directly (password signup/login, Google OAuth, Apple Sign In). Also starts the background scheduler on startup via `lifespan`.

CORS is restricted to `https://fellowscript.com`, `https://www.fellowscript.com`, and the local dev origin — not a wildcard. `/signup` (5/min) and `/login` (10/min) are rate-limited per-IP via `slowapi` to slow down brute-forcing and mass account creation; production sits behind Cloudflare, so the limiter keys off the `CF-Connecting-IP` header (`get_client_ip()`) rather than `request.client.host`, which would otherwise resolve to a rotating Cloudflare edge IP and never actually limit anything.

Auth routes in `main.py`:

| Route | Method | Description |
|---|---|---|
| `/signup` | POST | Register with username + password; creates free-plan subscription |
| `/login` | POST | Authenticate with username + password |
| `/auth/google` | POST | Validate Google ID token; find-or-create user |
| `/auth/apple` | POST | Verify Apple JWT (JWKS); find-or-create user |
| `/user/{user_id}` | GET / PUT / DELETE | Read, update, or permanently delete a user account |
| `/auth/password-reset/request` | POST | Email a single-use, 30-minute reset link if the address has an account (always returns the same generic response either way) |
| `/auth/password-reset/confirm` | POST | Set a new password from a reset token; invalidates every existing session on the account |
| `/auth/mfa/enable` | POST | Email a confirmation code to start turning on 2FA (authenticated) |
| `/auth/mfa/confirm` | POST | Verify the confirmation code and turn 2FA on (authenticated) |
| `/auth/mfa/disable` | POST | Turn 2FA off; requires re-entering the current password (authenticated) |
| `/auth/mfa/verify-login` | POST | Complete a login paused by `/login` for 2FA: verify the emailed code and issue the session |
| `/user/{user_id}/accept-terms` | POST | Record acceptance of the current Terms version (authenticated) |

Web-only 2FA: if a user has 2FA enabled, `/login` doesn't issue a session — it emails a 6-digit code and returns `{"mfa_required": true, "user_id": ...}`; the frontend then calls `/auth/mfa/verify-login` to finish. Not implemented on iOS yet.

**EULA gate (Guideline 1.2)**: `/signup`, `/auth/google`, and `/auth/apple` all require `terms_accepted: true` on new-account creation (422 otherwise) — enforced on all three since Apple may review via any of them. `CURRENT_TERMS_VERSION` (`schemas/users.py`) is stamped on every new account; if an existing account's stored version doesn't match on login, the response includes `terms_reaccept_required: true` and the client shows a blocking "Updated Terms" screen before calling `/user/{id}/accept-terms`. Accounts with `users.suspended_at` set (via the moderation CLI, see below) get a 403 on every auth path instead of a session.

**Apple name/email fallback**: Apple only ever supplies `full_name`/`email` to the client on the very first authorization for a given Apple ID + app — a missed or incomplete grant (e.g. the user already authorized this app before, in testing or otherwise) can never be recovered from Apple again. `/auth/apple` sets `users.needs_profile_completion = true` on account creation whenever either is missing, and the response (and every subsequent `/auth/apple`, `/login`, `GET /user/{id}` response, since it's just another user field) includes it so the client can prompt the user to set a real username/email manually. `PUT /user/{id}` clears the flag as soon as a `username` or `email` is supplied.

## Layer 2 — `backend/interactions/`

All business logic lives here in `*Manager` classes that subclass `DBManager`. Routes never touch SQL directly.

| Manager | File | Responsibility |
|---|---|---|
| `GroupsManager` | `groups.py` | Create/join/leave groups, add members |
| `FriendsManager` | `friends.py` | Friend requests, friend list, remove, friend-activity read surface (`get_friend_activity`) |
| `DevotionManager` | `devotion.py` | Devotion plans, participants, progress; `is_join_window_open` gates `join`/`join-call` on `time_start`/`time_end` (± `SESSION_JOIN_GRACE_MINUTES`), server clock only — see [Session join-window gating](../api/overview.md#session-join-window-gating-task-20260920-session-join-window-gating) |
| `AgentManager` | `agent.py` | AI agent config, heartbeat events, heartbeat timeline-instruction planning (2026-09-06) |
| `FilterManager` | `filtering.py` | Note filtering by book, date, user, title |
| `SortingManager` | `sorting.py` | Note sorting by timestamp |

`DBManager` (in `db.py`) provides four auto-committing helpers: `insertion`, `lookup`, `update`, `delete`. Raw cursor (`self.cur.execute`) is used for JOINs, array ops, and aggregations.

`insertion`/`update`/`delete` return an explicit `bool` — `True` on success, `False` on a caught DB error, and (for `update`/`delete` only) also `False` on a real no-op (zero rows matched, no exception). Callers must check this signal rather than assume success: at a call site where the target row's existence was just confirmed, a `False` return is raised as `SaveFailedError` (`backend/errors.py`) — a plain exception most routes just let propagate, since `main.py` registers an app-wide handler that turns it into a `503 "Couldn't be saved. Please try again."` response, the same way `slowapi`'s `RateLimitExceeded` is wired up. A call site doing best-effort/idempotent cleanup (e.g. severing a friendship that may only exist in one direction) treats `False` as an acceptable no-op instead. A caught DB error is also logged with a dedicated `DB_WRITE_FAILURE` marker so the CloudWatch watchdog (`backend/monitoring/watchdog.py`) can classify it separately from other error types.

## `backend/monitoring/`

A sibling package to `interactions/` for the CloudWatch-based error monitoring workflow (poll → detect → assemble context → persist → diagnose → serve).

| File | Responsibility |
|---|---|
| `cloudwatch_mcp_client.py` | `CloudWatchMCPClient` — async wrapper over the read-only `cloudwatch-mcp-server` (Logs Insights query + `analyze_log_group`). |
| `watchdog.py` | `WatchdogManager(DBManager)` — per-log-group cursor bookkeeping, error-signal regex scan, context assembly, and detection persistence (`run_cycle`); also the read methods (`list_detections`, `count_detections`, `get_detection`) backing the `/monitoring` routes. Right after a detection persists, `run_cycle` hands it off to `debug_agent.run_debug_agent_for_detection` (offloaded via `run_in_executor` so the blocking OpenRouter call never stalls the event loop). |
| `debug_agent.py` | `DebugAgentManager(DBManager)` — the error-debugging agent. Given a detection's `message` + `context`, redacts anything shaped like a secret/credential/API key/connection-string password, then calls OpenRouter (reusing `AgentManager`'s `MODELNAME`/`BASEURL`/`HEADERS` wiring — no second isolated credential) for a root-cause + remediation-narrative diagnostic report, persists it to `error_detection_reports` (upsert on `detection_id`), and routes the detection's `status` to `"diagnosed"`. Strictly read-only/reporting: no shell, system, or AWS-write access, and the model is explicitly instructed to describe recommended remediation steps, never narrate one as already taken. |

Detection is application-level (regex scan of pulled log messages against named signal patterns — traceback, critical, error level, nginx severity tags, HTTP 5xx, errno) rather than CloudWatch alarms/metric filters, which aren't configured in this AWS account. Nothing in this package executes or takes any action against the server — the watchdog only reads via the MCP client and writes to this app's own `error_detections`/`log_group_cursors` tables, and the debugging agent only reads those tables plus calls OpenRouter for a text diagnosis it persists to `error_detection_reports`.

## `backend/subscription/`

A sibling package to `interactions/` dedicated to billing and usage enforcement.

| File | Responsibility |
|---|---|
| `subscriptions.py` | `SubscriptionsManager` — create free plan, get subscription, reconcile expired, grant admin comp membership |
| `limits.py` | `LimitsManager` — `is_subscribed()`, per-resource usage counts, `check()` |
| `stripe_service.py` | Stripe Checkout session creation and webhook handling |
| `apple_service.py` | Apple App Store receipt/notification validation |

Every new user (all three auth paths) gets a `plan_type='free'` subscription row created by `SubscriptionsManager.create_free_plan()`. Free-tier limits (`FREE_LIMITS`: notes 10/week, agent_events 1) are enforced server-side via `check_limit(user_id, resource)` — which returns a 403-able gate dict — at **every** write path that creates a gated resource, so the cap holds for web and iOS alike. The full enforcement surface: notes → `POST /notes/{user_id}` (`create_note`), `POST /notes/reply/{note_id}` (`post_reply`), and `POST /agent/{user_id}/{agent_id}/summarize` (`summarize_session`, whose AI summary is persisted as a note) — all three count against the one weekly notes cap; agent_events → `POST /agent/{user_id}/{agent_id}/heartbeat` (`add_heartbeat`, the only heartbeat-insert path). The former `agent_notifications` gated resource (a cap on user-authored "agentic" notifications) was removed along with that subsystem (2026-08-26). When auditing, the invariant to preserve is: **any new route that inserts into `notes` or `agent_heartbeats` must call `check_limit` first** (a subscribed user is reported `unlimited` and always allowed). **Per-note character cap** (task 20260929-free-note-char-cap): users are capped per note: `FREE_NOTE_CHAR_LIMIT` = 30,000 characters (~5000 words x ~6 chars) on the free plan, `PAID_NOTE_CHAR_LIMIT` = 100,000 on paid plans of note `text` (Python `len`, code points; titles not counted), so the notes-count cap can't be dodged by growing one note. `LimitsManager.check_note_chars` / `check_note_chars()` returns a `check_limit`-shaped dict (`resource: "note_chars"`) that `create_note`, `post_reply` and `update_note` turn into a 403. Grandfather rule: reject iff `new_len > cap AND new_len > old_len` (create: `new_len > cap`), so shrinking/equal edits and deletes always work, including after a downgrade; `update_note` locks the row (`SELECT ... FOR UPDATE`) to read `old_len` in the same transaction. The acting editor's plan applies (group editors included) and never changes who may edit. The paid limit is a real plan limit enforced by the same rules (grandfather rule included); `/notes` POST/PUT bodies over `NOTES_MAX_BODY_BYTES` get 413 from a `Content-Length` middleware. AI-generated notes (`summarize_session`, heartbeat `note_via_hb`) are deliberately exempt from the char cap (never truncated) but still hit the notes-count gate. Clients read the caller's per-plan limit from `usage_summary()["note_chars"]` (`{unlimited: false, limit}`) (`GET /subscriptions/user/{id}/usage`). Fails closed: a plan-lookup error aborts the write. That free row is internal bookkeeping only — `GET /subscriptions/user/{id}` (`get_user_subscription`) reports a free-tier user as **`404`/no plan**, never as the free row, so clients render the upgrade UI instead of painting the free tier as an active plan (`LimitsManager.is_subscribed` applies the same `plan_type != 'free'` rule). Returning the free row here is what made the iOS Account screen show an active "Group Plan · $0/mo" with "Unlimited" usage for brand-new accounts.

There is a single paid tier, `'group'`, covering however many people (1-8) the host selects. `schemas/subscription.py`'s `GROUP_PRICE_CENTS` dict is the server-authoritative price-by-member-count lookup (`price_for(member_count)`), replacing the old two-tier `individual`/`group` model. **Price cut 2026-10-01** (task 20261001-subscription-price-cut): 1 member = $4.99 (pinned), 2-8 members = old tier price x 0.45 rounded half-up to 5 cents (cents `499, 810, 1215, 1620, 2025, 2430, 2835, 3240`; old `1000, 1799, 2699, 3599, 4499, 5399, 6299, 7199`). Existing Stripe subscribers and the Apple promotional offers are moved by hand-run, dry-run-first scripts (`api/scripts/stripe_price_migration.py`, `api/scripts/apple_price_and_promos.py`) following `docs/architecture/price-cut-runbook.md`; Apple's own USD prices legitimately differ from this table at some tiers (tier 4 is $36.99 on Apple vs $35.99 here), so Apple targets are computed from Apple's actual current price, never from this table. `stripe_service.create_checkout_session` builds the Stripe Checkout line item's price inline from this table for any count (no pre-created Stripe Products needed); `apple_service.APPLE_PRODUCTS` maps 8 fixed-price StoreKit product IDs (`com.fellowscript.access.one`…`com.fellowscript.access.eight`) to their member count, since Apple IAP can't compute an arbitrary price. A host can change their plan's member count later via `PUT /subscriptions/{id}` with `member_count`, which re-derives `price_cents`/`max_members`.

**Web trial length (`TRIAL_MONTHS`, task 20260930-creator-friend-codes step 1).** `stripe_service.create_checkout_session` no longer hard-sets `trial_period_days`. The trial is driven by the `TRIAL_MONTHS` env var (integer, `0` = no trial, no implicit default), parsed eagerly at boot by `stripe_service.validate_trial_config()` (called from `main.py`'s lifespan; unset or invalid refuses to boot) and read via `trial_months()`. When it is `0`, `trial_period_days` is omitted and the buyer is charged immediately; when `> 0` it is `TRIAL_MONTHS * 30` days. It is independent of any promo-code flag. `schemas.subscription.TRIAL_MONTHS` remains only for the internal `SubscriptionsManager.create_subscription` path. Webhook handling of `trialing` subscriptions is unchanged, so users already in a trial are unaffected.

*Rollout (billing change for ALL new web subscribers):* (1) set `TRIAL_MONTHS=0` in the local `.env`, in the production server's `~/fellowscript-docker/.env` (and the legacy `~/fellowscript/.env` if still used), and in the CI test env block of `.github/workflows/build-push.yml` (already added); (2) set it on the server BEFORE deploying the new image, since the app now refuses to boot without it; (3) deploy, then verify a test checkout shows no trial and charges immediately; (4) update user-facing copy (frontend/docs/Terms/SEO, handled in the copy-audit step) in the same release window. Apple introductory offers are configured in App Store Connect, not this repo, so iOS keeps its trial until removed there (flagged follow-up; web and iOS diverge until then).

**Creator Affiliates page API (task 20261007-affiliates-page).** `GET /affiliates/overview`, `GET /affiliates/resources`, `GET /affiliates/resources/{key}/file` (`routes/affiliates.py`, `backend/subscription/affiliates.py`, `affiliates_config.py`). Gated by the DB flag `affiliates` (off/on, default off; uniform 404 before auth when off). The caller is resolved only from the session: the session user's account email must equal (case-insensitive) the `owner_email` of an active, non-deleted creator code on an active creator, otherwise 403 with no data (no client-supplied id exists). Responses are aggregates only: active paying subscribers (referred buyers with a `subscriptions` row `status='active'`, non-free, `price_cents > 0`; trials excluded), monthly earnings = `commission_rate` x summed monthly plan price, new/total referred subscriptions per day/week/month (UTC), and milestone flags. Reached tiers are persisted once in `affiliate_milestones` (keyed by owner email) so churn never un-earns them; payouts stay manual. Tunables (commission rate 0.20, recurring for the life of each paying subscription, milestone tiers/bonuses, series lengths, link format, rate limit, resource manifest) live in `api/config/affiliates.json`. Resource files are copied from `data/` into `api/assets/affiliates/` by `scripts/sync_affiliate_assets.py` because the image contains only `api/`. Note: signup does not verify email ownership, so "verified email" is the account email on the authenticated session.

**Promo codes (task 20260930-creator-friend-codes, phase 1: web/Stripe).** Creator codes (admin-created, linked to a `creators` row) and friend invite codes (one per user, generated on demand) give a *new individual subscriber* the configured `PROMO_DISCOUNT_PERCENT` (50) off their first month. Code: `backend/subscription/promo.py` (config, `PromoManager`), `routes/promo.py` (user + admin endpoints), checkout/webhook hooks in `routes/subscription.py`, coupon + Stripe history lookup in `stripe_service.py`.

- *Config* (env, eagerly validated by `validate_promo_config()` in the lifespan, no defaults, all three places: local `.env`, server `~/fellowscript-docker/.env` (and legacy `~/fellowscript/.env`), CI env in `build-push.yml`): `PROMO_CODES_ENABLED` (`true`/`false`; deploy `false`), `PROMO_DISCOUNT_PERCENT` (1-100), `PROMO_VALIDATE_RATE_LIMIT` (e.g. `10/minute`). Set these on the server BEFORE deploying or the app refuses to boot. Enabling the flag is a manual decision.
- *Flag off*: all `/promo/*` and `/admin/promo/*` routes return a uniform 404 before auth; checkout ignores `promo_code` and is not rate-limited by the promo limit.
- *Stripe model*: DB is authoritative. One shared coupon `fellowscript-first-month-{pct}pct` (`percent_off`, `duration=once`) is created lazily and applied via `discounts=[{coupon}]` at session creation; `promo_code_id` rides in session/subscription metadata. No per-code Stripe promotion codes. Pricing stays server-side (`price_for`).
- *Rules enforced server-side* (`PromoManager.evaluate`, run at validate AND at checkout creation): code normalized (trim/uppercase, case-insensitive), active, not expired, under `max_redemptions`, creator active, not the caller's own friend code, `member_count == 1`, `TRIAL_MONTHS == 0` (no stacking), and buyer is a new subscriber: no `subscriber_history`, no stripe/apple non-free plan, not on a paid plan, no prior redemption (admin_comp and the free plan do not count), plus a Stripe lookup of customers by email with any non-incomplete subscription => ineligible. Any error, missing email, or ambiguous Stripe pagination denies. Buyer eligibility is computed before the code lookup so timing does not reveal whether a code exists. Every failure yields the same `{valid:false}` (validate) or `400 invalid_promo_code` (checkout).
- *Redemption logging*: only in `checkout.session.completed`, before the plan upsert (so a retry is not mistaken for a returning subscriber). Logged only if `payment_status == 'paid'`, `total_details.amount_discount > 0`, individual plan, not self-referral, and no prior local paid history. `PromoManager.log_redemption` locks the code row, conditionally increments `redemption_count` (cap), inserts with `ON CONFLICT (idempotency_key) DO NOTHING` and rolls back on a replay, so retries never duplicate or double-count. Over-cap at webhook time is stored with `over_cap=true` for admin review; the purchase is not reversed. Errors 500 so Stripe retries. Typing a code or abandoning checkout logs nothing.
- *Refunds/cancels*: log-only; rows are kept. *Friend link*: `SITE_URL/?code=CODE`, carried through signup by the frontend, always re-validated server-side. *Audit*: admin mutations emit `admin_audit` lines (ids only); logs never contain code text or emails.
- *Admin*: endpoints only (`require_admin`), no admin UI.

**Phase 2 (iOS) proposal, not implemented.** Apple forbids client-only discounts for digital subscriptions, so the web mechanism cannot be reused. Option A, offer codes: Apple generates redeemable codes per creator in App Store Connect; users redeem in the App Store (or via `presentCodeRedemptionSheet`). Pros: no signing server, Apple handles eligibility and abuse. Cons: no in-app text field flow of our own, codes are generated in bulk in App Store Connect, friend codes (per user, dynamic) are impractical, and our DB cannot be authoritative for cap/expiry. Option B, server-signed promotional offers: the app sends a code to our server; the server runs the same `PromoManager.evaluate`, then returns an ES256 signature (key from App Store Connect, `keyIdentifier`, `nonce`, `timestamp`, `productIdentifier`, `offerIdentifier`, `applicationUsername` = a per-user token) that StoreKit 2 uses via `Product.PurchaseOption.promotionalOffer`. Pros: one DB-authoritative code system for creators and friends, same rate limit and fail-closed rules. Cons: Apple promotional offers are for existing/lapsed subscribers only (not new ones), so a first-month discount for brand-new subscribers is not expressible this way; new-subscriber discounts on iOS must use introductory offers (configured in App Store Connect, not per code) or offer codes. Recommendation: use offer codes (Option A) for creator codes on iOS (creator-specific code batches give attribution), attribute redemptions through App Store Server Notifications (`OFFER_REDEEMED`/`SUBSCRIBED` with `offerIdentifier`, handled in `apple_service.py` and `/subscriptions/apple/notifications`, logging a `promo_redemptions` row with `platform='apple'`, `idempotency_key` = the transaction id), and treat friend codes as web-only until a signed-offer-eligible use case exists. Eligibility follows Apple subscription-group rules. Needs a separate decision and build before any iOS work. Separately, removing the iOS introductory trial in App Store Connect is a flagged manual follow-up; web and iOS trial behavior diverge until then.

**Owner rewards (task 20261001-promo-owner-rewards).** The owner of a code earns a reward worth `OWNER_REWARD_PERCENT` (50) off their NEXT month. Code: `backend/subscription/owner_rewards.py` (config, `RewardManager`, fail-closed entry points), `apple_service.sign_promotional_offer`, `stripe_service.apply_owner_reward`, routes in `routes/promo.py`, hooks in `main.py` signup flows and `routes/subscription.py`. Behind its own flag, deploy OFF; requires `PROMO_CODES_ENABLED=true` when on.

- *Config* (all env, no defaults, eagerly validated by `validate_owner_rewards_config()` in the lifespan, three places: local `.env`, server `~/fellowscript-docker/.env` + legacy `~/fellowscript/.env`, CI env in `build-push.yml`; the app refuses to boot if any is missing/invalid, including with the flag off): `OWNER_REWARDS_ENABLED`, `OWNER_REWARD_PERCENT` (1-100), `OWNER_REWARD_EXPIRY_DAYS`, `OWNER_REWARD_CAP_COUNT` + `OWNER_REWARD_CAP_WINDOW_DAYS` (max rewards earned per owner per rolling window), `OWNER_REWARD_MAX_OUTSTANDING` (max earned-unclaimed per owner), `OWNER_REWARD_IP_CAP_COUNT` (max signup rewards credited per client IP per window), `OWNER_REWARD_CLAIM_RATE_LIMIT`, `OWNER_REWARD_APPLE_RESERVATION_MINUTES`, `OWNER_REWARD_HASH_SALT` (>=16 chars, HMAC key for email/IP hashes), `APPLE_PROMO_KEY_ID`, `APPLE_PROMO_KEY_PATH`, `APPLE_PROMO_OFFERS` (JSON `{productId: offerIdentifier}` covering exactly the 8 products: after the price cut the codes are the versioned `invite_reward_50_v2` for `...access.one`, `invite_reward_50_v2_2` .. `_8` for two..eight, created at 50% of the new Apple prices by `apple_price_and_promos.py promos`; the legacy unversioned `invite_reward_50[_N]` offers were at 50% of the old prices and are deleted after the env switch. The validator already accepts any `[A-Za-z0-9_]{1,64}` id, so no code change was needed. The three places are updated together at the env-switch step of the runbook; the CI value in `build-push.yml` already uses the v2 codes), plus the existing `APPLE_BUNDLE_ID`. The owner must hold an individual (`max_members=1`), `active`, paid Stripe/Apple plan as its host at earn time; free, admin_comp, group, trialing or lapsed owners get nothing and the reward is dropped, not held (audited). Both hooks swallow errors (no reward, signup/webhook unaffected). Trigger (a) swallows errors (no reward, signup unaffected). Trigger (b) is retry-safe, see *Retry-safe purchase crediting* below. - *Stacking*: rewards queue FIFO, one applied at a time (one per billing month).
- *Stripe owner* (automatic): `apply_owner_reward` attaches the shared once-off coupon `fellowscript-owner-reward-{pct}pct` to the owner's Stripe subscription (next invoice) and the row is marked `claimed` in the same transaction (`FOR UPDATE SKIP LOCKED`); subscription metadata `owner_reward_id` makes a crash-then-retry recognize its own prior apply. It defers (reward stays earned) if the subscription is not `active`, is set to cancel, or already carries any discount. Re-attempted on earn and on every `customer.subscription.updated` for an active sub (a renewal consumes the previous coupon, then the next reward queues). No new Stripe webhook event types are needed.
- *Apple owner* (claim in app): `POST /rewards/{user_id}/apple/claim` (authenticated owner, rate-limited) requires an earned unexpired reward and an Apple individual subscription whose product is in the offer map; it reserves the oldest reward (fresh nonce, one outstanding signature per owner, else 409) and returns `keyIdentifier, nonce, timestamp, signature (base64 DER ES256), productIdentifier, offerIdentifier, applicationUsername`. Signed string: `bundleId, keyId, productId, offerId, applicationUsername, nonce, timestamp` joined with U+2063. `applicationUsername` is the claim's own nonce (a fresh lowercase UUID per signature); the client sets it as the purchase `appAccountToken` (`StoreKitManager` already uses the response's `applicationUsername`, so no iOS change), which makes the verified transaction echo the nonce back. See *Apple double-claim protection* below. The reward flips to `claimed` only when a verified Apple transaction with `offerType == 2` and a mapped `offerIdentifier` arrives via `/subscriptions/apple/sync` or an App Store notification (`OFFER_REDEEMED`/`DID_RENEW`/`SUBSCRIBED`; notification DB errors 500 so Apple retries), idempotent on the transaction id, and only when its `appAccountToken` equals a reward's current ledger nonce. An unredeemed signature blocks a re-claim until it is provably dead (below). `GET /rewards/{user_id}` returns counts and `can_claim_apple` (the legacy per-user `apple_application_username` field is still returned for client decode compatibility but is no longer what gets signed).
- *Retry-safe purchase crediting (task 20261001-owner-rewards-security-fixes).* Before, `credit_purchase_reward` swallowed errors and the `checkout.session.completed` replay returned early once the redemption row existed, so one transient DB failure permanently dropped a legitimate reward. Now `_log_promo_redemption` returns `(code_id, buyer_id)` whenever the session has a counted (not `over_cap`) redemption on record, whether logged just now, by an earlier delivery, or by a concurrent one (`PromoManager.get_redemption` reads the stored row). The webhook then calls `credit_purchase_reward` AFTER the buyer's plan upsert, so a crediting failure can never block the buyer's activation. `credit_purchase_reward` logs the exception class and re-raises; the webhook's existing `except` turns that into a 500 so Stripe re-delivers, and the replay re-attempts crediting. Idempotency: the reward key is `purchase:<Checkout Session id>` (UNIQUE, `ON CONFLICT DO NOTHING` under the per-owner advisory lock); `earn_purchase` also checks the key up front so replaying an already-credited purchase is a clean no-op (no spurious `reward_skipped_*` audit, no double-grant, concurrent deliveries yield exactly one reward). Fail closed is unchanged: ineligible/permanent outcomes (no owner, owner not subscribed, cap, self-referral, over-cap redemption, unknown code) return normally, grant nothing and the webhook answers 200 (no retry loop). Webhook replay is the reconcile path; no new route or cron exists. Residual: the Stripe discount application (`apply_stripe_reward`) stays best-effort and leaves the reward `earned` for the next `customer.subscription.updated`. Example: delivery 1 logs the redemption, crediting hits a DB blip, webhook 500; Stripe retries, the redemption exists, crediting runs again and inserts the reward; a third delivery finds the reward and does nothing.
- *Apple double-claim protection (task 20261001-owner-rewards-security-fixes).* Problem: a promotional-offer signature stays redeemable at Apple after our own reservation lapses, so re-signing on lapse could let one reward yield two discounted months. Mechanism: (1) every signature's nonce is a fresh UUID stored in `owner_rewards.apple_nonce` (now UNIQUE where not null), also used as `applicationUsername`, so the transaction's `appAccountToken` identifies exactly which signature was redeemed. (2) New column `apple_signature_expires_at` = signing time + 24h Apple signature validity + 1h clock-skew margin (`APPLE_SIGNATURE_VALID_HOURS`, `APPLE_SIGNATURE_SKEW_MARGIN_HOURS`; protocol constants, signed timestamp and death time both come from the DB clock). The 24h validity is Apple's documented window and is the one external assumption here. (3) `claim_apple` returns 409 while ANY earned reward of the owner has a possibly-live signature, so `OWNER_REWARD_APPLE_RESERVATION_MINUTES` no longer gates re-issue (it still sets `apple_reserved_until` as an in-progress hint); only after the old signature is provably dead is the reward re-signed, replacing the ledger nonce so the old one can never finalize. `_expire_due` also skips rewards with a live signature so a reward cannot expire out from under a redeemable offer. A user who dismissed the sheet therefore waits up to about 25h (security preferred over convenience). (4) `finalize_apple_claim(user, txn, product, offer, appAccountToken)` locks the owner, is idempotent on the transaction id, finds the reward by `(owner, apple_nonce = token)` (stale, unknown, foreign or missing token matches nothing and is audited `reward_apple_redeemed_unmatched`), and claims with an atomic conditional `UPDATE ... WHERE status='earned' AND apple_nonce=<token>` (at most one finalization per reward; a second transaction with an already-finalized nonce is audited `reward_apple_duplicate_redemption` and grants nothing). Covers `/apple/sync` and `/apple/notifications` since both go through `reconcile_apple_offer`. All claim and finalize steps run under the per-owner `pg_advisory_xact_lock`. Migration: additive `ALTER TABLE ... ADD COLUMN IF NOT EXISTS apple_signature_expires_at` plus a partial unique index on `apple_nonce` (db.py, idempotent). Backend only: iOS already passes the response's `applicationUsername` as `appAccountToken`.
- *Admin/user surface*: admin-only creator-code creation attached to an email (secure generated `FS-` + 12 CSPRNG chars unless a code is supplied), deactivation, reactivation (only flips `active`; expiry/cap/creator checks still apply), soft delete of creator codes (`promo_codes.deleted_at`; friend codes rejected with 422; deleted codes vanish from lists/overview/validate/PATCH and reactivate is 404, but `get_code_by_id` still resolves them so in-flight checkouts log redemptions and rewards; text stays reserved; all idempotent, audited with ids only), and an overview with redemption and reward counts; `promo_codes.owner_email` is also set on a user's friend code (the existing `POST /promo/{user_id}/friend-code` is the invite-link endpoint). Admin authz reuses `require_admin`. Awaiting-email creator codes (task 20261005-creator-promo-awaiting-email): `owner_email` is optional on creator-code creation; blank creates the code deactivated with `promo_codes.requires_owner_email = TRUE` (additive column, default FALSE so legacy codes are untouched). `awaiting_email` (derived: flag set and no email) is exposed on code lists/overview. Activate/reactivate of such a code is 409; `PATCH /admin/promo/codes/{id}` accepts `owner_email` (format-checked, 422; blank removes it, which sets the flag and deactivates the code); saving an email never auto-activates. `evaluate` fails closed for flagged codes with no email even if `active` is true. Email set/removal is audited in `promo_audit_log` (ids only, no email).
- *Known limits*: an iOS brand-new subscriber cannot receive a discount through our codes (Apple promotional offers are for existing/lapsed subscribers); they must subscribe on the web, where the first-month discount still applies. `owner_email` matching trusts that an account's email belongs to its holder (accounts are not email-verified), flagged for the security review. Invitees on the web keep the existing first-month 50% discount unchanged. Out of scope: payouts, group-plan rewards, auto-enabling the flag.

**iOS friend-invite redemption via Apple offer codes (task 20261003-ios-friend-offer-code-redeem).** Apple promotional offers only apply to current/lapsed subscribers, so a brand-new iOS subscriber redeems a friend code through an Apple *offer code* (offer eligibility "new subscribers", 50% off one month). Code: `backend/subscription/apple_offer_codes.py` (config, ASC client, `OfferCodeManager`, `reconcile_offer_code`), route `POST /promo/{user_id}/ios-offer-code` in `routes/promo.py`, reconcile hooks in `routes/subscription.py` (`/apple/sync`, `/apple/notifications`), table `ios_offer_redemptions` (`schema_ddl/ios_offer_redemptions.py`).

- *Manual prerequisite (the code never creates or edits an ASC offer).* In App Store Connect create ONE offer code on `com.fellowscript.access.one`: customer eligibility **New** only, pay-as-you-go/pay-up-front 50% off for 1 period, one-time-use codes allowed. Note its reference name (must equal `APPLE_OFFER_CODE_REFERENCE_NAME`; StoreKit echoes it as `offerIdentifier`) and its `subscriptionOfferCodes` resource id (`APPLE_OFFER_CODE_ID`). The ASC API key (`APPLE_ASC_KEY_ID`/`ISSUER_ID`/`KEY_PATH`) must be allowed to create one-time-use codes. At runtime the server does a cached (10 min) read-only `GET /v1/subscriptionOfferCodes/{id}` and refuses to mint unless the offer is active, new-subscribers-only and the name matches. Until then the local `.env` holds placeholders for `APPLE_ASC_ISSUER_ID` and `APPLE_OFFER_CODE_ID`.
- *Config* (env, no defaults, eagerly validated by `validate_offer_codes_config()` in the lifespan; three places: local `.env`, server `~/fellowscript-docker/.env` (+ legacy `~/fellowscript/.env`), CI env in `build-push.yml`): `IOS_OFFER_CODES_ENABLED` (deploy `false`; `true` also requires `PROMO_CODES_ENABLED` and `OWNER_REWARDS_ENABLED`), `IOS_OFFER_CODE_EXPIRY_DAYS` (7-180; pool batch validity), `IOS_OFFER_CODE_RATE_LIMIT` (per IP and per user), `IOS_OFFER_CODE_IP_DAILY_CAP` (issuances per HMAC-hashed client IP per 24h), `IOS_OFFER_CODE_DAILY_MINT_CAP` (global codes ISSUED per 24h), `IOS_OFFER_CODE_BATCH_SIZE` (codes per pool batch, 500-25000, default value 500), `IOS_OFFER_CODE_DAILY_BATCH_CAP` (ASC batch creations per 24h), `APPLE_ASC_KEY_ID`, `APPLE_ASC_ISSUER_ID`, `APPLE_ASC_KEY_PATH` (read only when enabled; never logged), `APPLE_OFFER_CODE_ID`, `APPLE_OFFER_CODE_REFERENCE_NAME`, `APPLE_APP_STORE_ID`. The app refuses to boot if any is missing, so set them on the server BEFORE deploying.
- *Flag off*: the route is a uniform 404, reconcile hooks do nothing.
- *Validate then issue from a pool.* `OfferCodeManager.request_code` reuses `PromoManager.evaluate` (code exists/active/unexpired/under cap, creator active, not the caller's own code, new subscriber by local history plus Stripe email lookup, `TRIAL_MONTHS == 0`), then requires a friend code, a client IP, an outstanding-aware cap (`redemption_count` + issued rows < `max_redemptions`), the per-IP and global issued-per-day caps. Every validation failure is the same `400 invalid_invite_code` and makes no ASC call. Apple rejects one-time-use batches under 500 codes (live-tested 2026-10-04: `numberOfCodes: 1` returns 409), so codes come from a POOL: `ios_offer_batches` rows (ASC batch id, size, expiry, `next_index`, `ready_at`). Only when no usable batch exists (none, exhausted, or expiring within a 3-day safety margin) does the server create one of `IOS_OFFER_CODE_BATCH_SIZE` codes via `POST /v1/subscriptionOfferCodeOneTimeUseCodes`; the row is committed `pending` before the call, creations are capped per day separately, and an unknown outcome blocks another create for an hour. ASC generates values asynchronously, so a batch is marked `ready_at` only once `GET .../values` returns the full count; until then requests get 503. Per issuance the server atomically takes the next index (`next_index + 1` under an advisory lock, `FOR UPDATE`), stores only (batch, index) on the user's redemption row, reads the batch values from ASC (sorted, so an index is stable) and returns the code at that index. Code values are never stored or logged. Response: `{offer_code, redeem_url, expires_at}` (`no-store`); the iOS app opens `AppStore.presentOfferCodeRedeemSheet` (or `redeem_url`).

The pool then uses it from index 0 and creates no other batch while it is active, has capacity and is not within 3 days of expiry. `ready_at` stays NULL; the first request reads `GET .../values` and marks it ready only if ASC returns exactly `number_of_codes` values (otherwise 503, fail closed).  
  ```sql
  INSERT INTO ios_offer_batches (asc_batch_id, status, number_of_codes, next_index, expires_at)
  VALUES ('607166', 'active', 500, 0, '2027-01-02 23:59:59+00')
  ON CONFLICT (asc_batch_id) WHERE asc_batch_id IS NOT NULL DO NOTHING;
  ```

  e.g. `docker compose exec <db-service> psql -U <user> -d <db> -c "<the INSERT above>"`. Check with `SELECT asc_batch_id, status, next_index, number_of_codes, ready_at FROM ios_offer_batches;`. The table is created by `create_tables` at app startup, so seed after the first boot of this release. The batch's offer must be the configured `APPLE_OFFER_CODE_ID`. If ASC's batch resource id differs from the number shown in the console, the values fetch fails closed and the row can be corrected with an UPDATE of `asc_batch_id`.
- *Idempotency / failure modes.* One live (`pending|issued|redeemed`) row per user (partial unique index) and one row per (batch, index) (unique). A retry while `issued` re-reads the SAME index, so a user never consumes a second code; `redeemed` is denied; an `issued` row past its expiry becomes `expired` and the user may be issued afresh. Failed rows (including the legacy single-code design's) never block a user; a legacy `pending` row is closed as `failed`. Pool exhaustion, ASC values not ready, a rejected or ambiguous batch create, the daily issued cap and the daily batch cap all fail closed with 503 and a `promo_audit_log` event, never a fabricated code. A reserved index whose values were not yet readable stays reserved for that user's retry.
- *Reward crediting only on the verified Apple transaction.* `reconcile_offer_code` runs from `/apple/sync` and from `OFFER_REDEEMED`/`SUBSCRIBED`/`DID_RENEW` notifications (any transaction with an `offerIdentifier`), acts only on `offerType == 3`, `offerIdentifier == APPLE_OFFER_CODE_REFERENCE_NAME`, individual product. Correlation key: the transaction's user (sync: authenticated caller; notification: owner of the original transaction id) + that user's `issued` redemption row + offer identifier + transaction id (unique). Apple does not report which code was used, so a code handed to someone else matches no row for them and is audited `ios_offer_redeemed_unmatched` with no reward. On match: row -> `redeemed`, a `promo_redemptions` row (`platform='apple'`, key `ios-offer:<row id>`, cap enforced atomically) and the owner reward via the same ledger as signups (key `signup:<invitee id>` plus the per-invitee/per-email unique indexes). A user who also sent `invite_code` at signup was already credited at signup, so the offer path cannot create a second reward. Replays complete any missed step and never duplicate (notification DB errors 500 so Apple retries; sync logs and the app re-syncs on launch).
- *Audit/redaction.* `promo_audit_log` actions `ios_offer_issued|expired|ip_capped|daily_capped|legacy_pending_closed|code_not_ready|pool_not_ready|pool_exhausted|batch_reserved|batch_created|batch_failed|batch_ambiguous|batch_pending_blocked|batch_capped|redeemed|redeemed_unmatched`; ids only. ASC errors log the HTTP status only; no tokens, bodies or code values.
- *Known limits.* Eligibility "new subscriber" is our check (local + Stripe) AND Apple's own offer eligibility; the ASC offer must be New-only or Apple will not enforce it. Offer-code redemption by someone other than the requesting account earns no owner reward (by design).

There is also a separate, admin-only `plan_type='individual'` row shape (`provider='admin_comp'`), unrelated to the old pre-`GROUP_PRICE_CENTS` "Individual" tier described above — it's a $0, non-billed grant created via `POST /subscriptions/admin/grant-individual` (`require_admin`) for the app's own admin account(s) to get free unlimited access without going through Stripe/Apple. See `SubscriptionsManager.grant_admin_comp` and the API reference.

**Apple sync guards** (three layers, spanning both `POST /subscriptions/apple/sync` and `POST /subscriptions/apple/notifications`): iOS reports every currently-active StoreKit entitlement (`Transaction.currentEntitlements`) to `/apple/sync` on each launch — a device/Apple-ID-level API, not scoped to whichever FellowScript account is signed in — and Apple's servers push renewal/refund/cancel events to `/apple/notifications`, which (like the Stripe webhook) has no user session and authenticates purely via the payload's own signature.
1. **Signature verification (primary)**: `apple_service.decode_jws` verifies every JWS's `x5c` certificate chain against a pinned copy of Apple's Root CA - G3 before trusting any claim in the payload, then checks the ES256 signature itself. A JWS that doesn't chain to Apple's real root, or whose signature doesn't match, is rejected with `ValueError` (surfaced as `400`) before its payload is ever read — closing both the authenticated-user-forges-their-own-sync and the unauthenticated-anyone-forges-a-notification paths.
2. **Environment gate**: every StoreKit transaction carries an `environment` (`"Xcode"` = local `.storekit`-file testing, `"Sandbox"` = TestFlight/App Review, `"Production"` = real purchase). The route calls `apple_service.is_accepted_environment(...)` and rejects with `400` before touching the DB unless it's `Production` (always) or `Sandbox` (gated by `APPLE_ALLOW_SANDBOX`, which must be explicitly `"true"` or `"false"` — the process refuses to start if it's unset, no implicit default). This is what stops a dev device's fabricated `"Xcode"` transaction (id `"0"`) from turning every account signed in on that device into a paid plan — the actual cause of the repeated "new accounts show the paid plan" reports.
3. **Ownership guard (defense-in-depth)**: `upsert_from_apple` still returns `None` → `409` if the `apple_original_transaction_id` is already tied to a *different* `user_id`, so one real transaction can't be spread across accounts.

A message may now carry an image/video/file/gif attachment alongside or instead of `text` — nullable `attachment_kind` / `attachment_key` / `attachment_meta` columns on the existing `messages` table (no new table). Handled entirely within the existing three-layer flow rather than a new subsystem:

| File | Responsibility |
|---|---|
| `backend/interactions/attachments.py` | Presigned S3 upload/download for **image/video/file** attachments only. `generate_upload_policy(user_id, attachment_kind, content_type)` issues a presigned S3 **POST** policy (not a bare PUT — only a POST policy's conditions can cryptographically bind content-length-range and an exact content-type) scoped to a server-derived object key (`attachments/{user_id}/{uuid4()}{ext}` — never a client-supplied filename/extension) and fails closed (`ValueError`) on any attachment_kind/content_type combination outside the per-kind allowlist (`PER_KIND_LIMITS`: image ≤15MB, video ≤250MB, file ≤50MB — a documented, deliberately curated MIME allowlist per kind, e.g. `application/zip` is excluded from "file" as a common malware vector). `generate_download_url(object_key)` issues a fresh, short-lived (1hr) presigned GET at read time — the object key itself is never handed to a client, only ever the DB-stored reference. ## Main-chat send guard (task 20261002-ws-send-hardening)

`backend/interactions/send_guard.py` (`authorize_send`) is the single owner of main-chat WebSocket send authorization, called once from `ConnectionManager.send_msg` before the block check and `save_message`. It is stateless; every query goes through the `_GuardCursor` adapter into `ConnectionManager._execute`, so stale-cursor repair applies. Group sends require a current, non-suspended member and derive recipients from the group's live member list (client `to_users` ignored). DMs require exactly one existing friend who is not the sender. `image`/`video`/`file` attachment keys must be under `attachments/<sender_id>/`. Outcomes:

| Outcome | Cause | Sender sees |
|---|---|---|
| `SendDecision` | authorized | normal send |
| `Reject` | genuine authorization denial (non-member, non-friend, forged recipients, foreign attachment key, bad group id) | `{type: error, reason: not_allowed}` (uniform, cause logged internally only) |
| `Drop` | blocked DM | nothing (silent, as before) |
| `Unavailable` | infrastructure failure inside the guard (database unreachable, query error, timeout) | `{type: error, reason: send_failed}` (retriable) |

Both `Reject` and `Unavailable` fail closed: the message is not saved. The split exists so an outage is never reported to users as "not allowed"; clients can retry `send_failed` but should not retry `not_allowed`.

The former `_fire_due_notifications` job (fired user-authored "agentic" notifications on their scheduled time-of-day) was removed in full (2026-08-26) along with that subsystem, replaced by the fixed-notification jobs below (activity-tracked reminders + friend-went-active), backed by `backend/interactions/activity.py`'s `ActivityManager` and `user_activity` table.

**Heartbeat timeline instructions (2026-09-06).** Each heartbeat's future note content is now planned upfront rather than deduped reactively — see [`agent_heartbeats.timeline_instruction`](data.md#agents-agent_heartbeats) for the storage shape. `AgentManager.add_heartbeat` calls a dedicated timeline-planning LLM prompt (`backend/interactions/timeline_prompt.txt`, distinct from the note-writing agent's own `agent_prompt.txt`) synchronously at creation time — a heartbeat row is never inserted without a timeline, and generation failure (`TimelineGenerationError`, mapped to a `502` by an app-wide handler in `main.py`) aborts the whole create. ## Group invite links (task 20260929-group-invite-links)

`routes/invites.py` + `backend/interactions/invites.py` (`InvitesManager`, per-`kind` handler registry; only `'group'` today so phase 2 subscription-seat invites add a handler, no schema change). `invites` table (db.py): SHA-256 token hash only (256-bit CSPRNG tokens, plaintext returned once at creation), `kind`, untyped `target_id` (no FK; group delete/last-leave purges its invites in code), `expires_at`, `max_uses`, `use_count`, `revoked_at`. Redeem locks the group row, rejects blocked pairs (either direction, any current member), then a single `UPDATE ... WHERE use_count < max_uses AND not expired/revoked RETURNING` gates the join in the same transaction as the member append. Tunables and the feature flag (`enabled`, turned on 2026-09-30) live in `api/config/invites.json`, validated at startup (`invites_config.py`, no implicit defaults). Audit lines `INVITE_AUDIT ...` log only an 8-char hash prefix, never the token.

**Permanent group links and member cap (task 20260930-group-invite-permanent-member-cap).** Group (`kind 'group'`) links never expire: `invites.expires_at` is now nullable and group links store NULL (handler `permanent = True`; a client-sent `expires_in_days` is ignored). Usable-token SQL is `(expires_at IS NULL OR expires_at > NOW())`; existing group links keep their original expiry, and subscription links always keep a non-null expiry. Group `default_expiry_days`/`allowed_expiry_days` are deprecated (still required and validated so boot never breaks, but unused for groups). `groups.max_members` (nullable, NULL = unlimited) is the owner-set cap: `PUT /groups/{user_id}/{group_id}/max-members` (`{"max_members": int|null}`, creator only: 403 otherwise, 422 for non-int/bool, outside `[2, max_group_members_ceiling]`, or below the current member count; audited as `INVITE_AUDIT event=set_max_members`). New required key `max_group_members_ceiling` in `api/config/invites.json` (250). `GET /groups/{user_id}/{group_id}/info` adds `max_members`, `member_count`, `is_owner`, `max_members_ceiling`. Enforcement: invite redeem checks the cap under the group row lock (`409 group_full`; existing members stay idempotent; preview treats a full group as the uniform `not_found`), with a SQL guard in the append as defense in depth; `PUT /groups/{user_id}/{group_id}` (member-list replace) also locks the row and returns `409 group_full` when it would add members past the cap.

**Member removal revokes that member's group links (task 20261002-revoke-leaving-member-invite-links).** Group links are permanent, so a link must not outlive its creator's membership. `revoke_member_group_invites(cur, group_id, member_ids)` (`backend/interactions/invites.py`) sets `revoked_at = NOW()` (the same state manual revoke/reset use, no new state) on that member's active `kind='group'` links for the group, never touching `'subscription'` links; it only matches `revoked_at IS NULL` so it is idempotent, and logs `INVITE_AUDIT event=auto_revoke` with counts only (no tokens). It runs on the caller's cursor inside the same transaction, under the `groups` row `FOR UPDATE` lock that redeem and the member cap take first (lock order: group row, then invite rows, so no deadlock and a concurrent redeem either lands before the departure or finds the link revoked). Callers: `GroupsManager.leave_group` (now one transaction: lock, member list update, revoke, commit; the creator is treated like any other member, so a leaving creator's links are now revoked, a change from before) and `GroupsManager.update_group` (the PUT member-list replace revokes the links of every dropped member in the same transaction as the write; retained members keep theirs). These are the only writers that remove from `groups.users` (there is no separate owner-removal endpoint). Any failure rolls back both the membership change and the revoke (fail closed, `SaveFailedError`). Group delete and last-member leave still hard-delete all the group's invites (`purge_target_invites`; the last-member path is now in the same transaction as the group delete). A revoked link returns the same responses as any other revoked link. Rejoining never resurrects a revoked link.

*Backfill and deploy runbook note.* `db.backfill_revoke_departed_group_invites(cur)` revokes every active `kind='group'` link whose creator is no longer in that group's `users` (left or removed before this fix, or whose group is gone). It is idempotent (a second run matches nothing), additive, and is called from `create_tables`, so **it changes production data on the first startup after the next deploy** (a one-time revocation of orphaned links; log line `INVITE_AUDIT event=backfill_revoke_departed count=N`). Nothing was run against production in this task.

**Reveal ("Show link") for group links (task 20261002-group-invite-show-link).** New group links get an HMAC-derived token so they can be re-shown: `create` stores a random 32-byte `invites.reveal_nonce` (new nullable BYTEA, `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` in `create_tables`) and the token is `base64url_nopad(HMAC-SHA256(INVITE_LINK_SECRET, nonce))` (43 chars, 256-bit, same `_TOKEN_RE`). The SHA-256 `token_hash` is stored exactly as before, so preview/redeem/revoke are unchanged; the HMAC output is never stored, so a DB leak alone cannot reconstruct any link. `reveal_nonce IS NULL` means legacy (random token, unrecoverable) or subscription; those keep working for redeem but cannot be revealed. `GET /invites/{user_id}/{invite_id}/reveal` (authenticated, `Cache-Control: no-store`, gated by the `enabled` flag, limited by `rate_limits.reveal` and `reveal_per_user`) returns `{invite_id, url}` only for an active (not revoked/expired/exhausted) derived group link, to a current group member who is the link's creator or the group manager. Every failure (bad id, unknown, subscription, inactive, legacy, non-member, neither creator nor manager, or a recomputed token whose hash no longer matches the stored hash) returns the one uniform 404 `not_found`; the match is checked with `hmac.compare_digest`. Audit: `INVITE_AUDIT event=reveal ... as=creator|manager` (ids and 8-char ref only) and `event=reveal_miss reason=<code>` server-side only; the token is never logged. `GET .../groups/{group_id}` list items gain an additive boolean `revealable` (clients show "created before reveal was available - create a new link" when false). Config: `INVITE_LINK_SECRET` (env, required, >=32 chars, no default; `validate_invite_link_secret()` runs in the lifespan and the app refuses to boot without it; the value is never logged or echoed). Three places: local `.env`, server `~/fellowscript/.env` (manual step, needs explicit confirmation before the first deploy of this change), and the CI env block in `build-push.yml`. **Rotation:** changing the secret does not affect redeem/preview/revoke (hash only) but makes reveal fail (uniform 404) for every previously derived link; users then create new links. No key-versioning column (rotation only degrades reveal).

**Subscription-seat invites (phase 2, kind `'subscription'`; supersedes "only `'group'` today" above).** Handlers implement a kind-neutral interface (`lock_target`, `is_actor`, `is_manager`, `create_precheck`, `existing_outcome`, `redeem_precheck`, `apply`, `preview`, `purge`); the group handler's behavior is unchanged. `target_id` = `subscriptions._id`. Only the plan owner (`subscriptions.user_id`) can create/list/revoke/reset links (403 otherwise, including plan members), and only on an active, non-lapsed `group` plan with `max_members > 1` (`409 not_eligible` otherwise). Routes: `POST|GET /invites/{user_id}/subscriptions/{subscription_id}`, `POST .../reset`; preview/redeem/revoke are shared. Redeeming **never changes `users.subscription_id`**: it inserts a pending `subscription_request` (idempotent; a link use is consumed only when a new request row is created) that the owner accepts or declines via the existing `/subscriptions/{id}/requests` endpoints. Redeem rejects (uniform `not_found`) a plan that is ineligible, full, or at its pending-request cap; `409 other_plan` if the caller already sits on a different non-free plan; `403 blocked` for a block in either direction with the owner or any member. FOR UPDATE` on the subscriptions row (same lock redeem takes), so concurrent accepts cannot exceed `max_members`, and it refuses a requester who has since joined another paid plan. - **`FEATURE_SUMMARY`** (`backend/observability/feature_summary.py`): one hourly INFO line of counts only (public requests, 404s, 429s, shed requests, statement timeouts, probe-off hits, outbox backlog, pending join requests). It is the only visibility surface for 429 and probe traffic, which are deliberately not logged per request. Counts only, no ids or PII.

### Lifecycle hooks, S3 outbox and group member hygiene (shared foundation, step 3)

- **Lifecycle registries** (`backend/interactions/lifecycle.py`): four registries, `group_delete`, `member_leave`, `user_delete` and `listing_hidden`, with `register(kind, fn)` and `run(kind, cur, ...)`. Hooks run in the caller's open transaction and return S3 keys; the caller enqueues them with `enqueue_s3_deletes`. A hook that raises aborts the whole delete (chosen over silently losing keys). SF registers the group photo and announcement banner collectors (only keys the owning helper can prove belong to that group) and the `user_delete` member removal in `backend/lifecycle_wiring.py`, which imports other feature modules only at function level (`groups.py` imports `lifecycle`).
- **Outbox** (`pending_s3_deletes`, DDL module `outbox`, `backend/interactions/s3_outbox.py`): request paths (`delete_group`, `leave_group`, `delete_user`) only INSERT keys in the same transaction and never flush. A 60 s scheduler job (thin `async def`, work via `run_in_executor`) claims up to 200 rows `FOR UPDATE SKIP LOCKED`, deletes each object, drops the row on success and counts an attempt otherwise; rows at 20 attempts are given up on and kept. One aggregated WARNING per run with counts; at most one `S3_DELETE_DENIED` ERROR per key prefix per 24 h. The IAM user needs `s3:DeleteObject` on `group-photos/*` and `group-announcements/*` (action A1a) or every attempt is an aggregated AccessDenied. `attachments.delete_object` (single key, best effort) is unchanged and is not used by the outbox.
- **One transaction body for leaving.** `GroupsManager.remove_member_in_tx(cur, group_id, user_id)` is exactly the `leave_group` body (array remove, invite revoke, `member_leave` hooks, or last-member group delete with `group_delete` collectors and invite purge). `leave_group` and the `user_delete` hook both call it. `delete_group` now collects keys, enqueues, deletes the row and purges invites in one transaction.
- **Account deletion** (`DELETE /user/{id}`): before the user row goes, the `user_delete` hook removes the id from every group's member list (a last-member group is deleted). Before this, deleted ids stayed in `groups.users` and made later group sends fail. Existing dangling ids are cleaned by the operator-run `python -m backend.maintenance.prune_group_members` (dry run by default; `--apply` is one idempotent UPDATE that keeps array order; groups left empty are reported, never deleted).
- **Member validation.** `PUT /groups/{user_id}/{group_id}` drops ids that are already in the stored list but no longer exist (so build-78 clients that echo the raw array keep working). A NEW id must be a UUID of an existing, non-suspended user, otherwise `422 {"code": "invalid_member"}` (same body for malformed, unknown and suspended ids: no existence oracle). `POST /groups/{user_id}` applies the same rule to every supplied id (the creator's own id always passes).
- **Live member helper.** `groups.LIVE_MEMBER_JOIN` and `groups.live_member_ids(cur, group_id)` are the only place the `groups.users` to `users` join is written. The users side is matched with a CASE-guarded uuid cast of the array element (never `u._id::text = x`, which full-scans `users`; the CASE also stops a junk string raising a cast error). Readers (message authorship, recipients, member counts) import it.
- **Report and moderation registries.** `reports.CONTENT_RESOLVERS[type](cur, content_id, reported_user_id)` returns `(author_id, snippet, canonical_content_id)` or `None` (not found: the route answers 404 and stores nothing); `backend/moderation/removers.CONTENT_REMOVERS[type](cur, content_id)` replaces the CLI's if/elif chain (kept in its own module so the `python -m` run does not create a second registry). The five original types keep their lenient behaviour. `content_type` also accepts `group_listing` and `thread_message` (no resolver yet, so 404 until LST and THR register theirs). A malformed `content_id` is `422` (it used to be a 500); `group_listing` ids must match `^[0-9A-Za-z]{10}$`.
- **`backend/registrations.py` `load_all()`** imports every module that registers hooks, resolvers or removers; `main.py` (lifespan) and `backend.moderation.admin_actions` call it because the CLIs are separate processes. A content type with no registered remover makes the CLI exit non-zero instead of removing nothing. Later tasks add one import line each.

### Logging convention (C19) and the CloudWatch watchdog

The watchdog (`backend/monitoring/watchdog.py`) treats the bare word `ERROR` at any level as a detection, and each detection can cost an LLM triage call.

1. ERROR only for unexpected failures (DB write failure keeps its `DB_WRITE_FAILURE` marker; unhandled exceptions).
2. Expected denials, uniform 404s, flag-off hits, rate-limit hits, validation failures and public query timeouts are INFO or not logged. Text of non-error lines says "failed", never the bare word ERROR.
3. Retries and partial failures in sweepers, the outbox and notifiers: one WARNING per run with counts, never per key or per recipient.
4. At most one `S3_DELETE_DENIED` ERROR per prefix per 24 h.
5. No usernames, emails, message or listing text, cursor values or presigned URLs in any line; ids only.

**nginx access-log rule.** The watchdog also scans `/fellowscript/nginx/access` every 90 s: every 5xx line is a per-line `http_5xx` detection and 30 4xx lines in a window raise a 4xx anomaly (up to 25 LLM triage calls per cycle). So public surfaces answer an expected "off" state with `200` and a body (never 404), and shed load with `429` plus `Retry-After` (never 503).

### Rules for new code

- **R-SCHED.** Every new scheduler job is a thin `async def` registered with `scheduler.add_job(..., id=..., replace_existing=True)`; all psycopg2, boto3 and SES work runs through `await loop.run_in_executor(None, sync_fn)`; one aggregated WARNING per run with counts; no per-key or per-recipient log lines.
- **R-ROUTE.** New authenticated routes are plain `def` (FastAPI runs them in the threadpool), because some take `FOR UPDATE` locks and a lock wait on the event loop would freeze every WebSocket. Public routes use `run_public` (added later in this task). Existing `async def` routes are not rewritten.

### Edge and runtime hardening (step 5)

- **Client IP.** `backend/rate_limiting.py` `get_client_ip` trusts `CF-Connecting-IP` only when the TCP peer is loopback (nginx) or the test client, and only when the value parses as an IP; otherwise the peer is the rate-limit key. `X-Real-IP` is never read. The Dockerfile starts uvicorn with `--no-proxy-headers` so the peer is not rewritten; the two must ship together. `ops/nginx/real-ip.conf` (prepared, not applied) makes nginx overwrite the header.
- **WebSocket registry.** `ConnectionManager.disconnect(user_id, ws)` removes an entry only if that socket is still the registered one, so an old socket's cleanup cannot evict a newer connection. The heartbeat loop calls `evict_suspended()` about once a minute and closes sockets of suspended accounts with code 1008.
- **Public API isolation.** `backend/public_guard.py` runs public handlers' blocking work on a dedicated `anyio.CapacityLimiter` (`configure(concurrency, max_waiting)` once at startup, no defaults). Overload and statement timeouts answer 429 `{"code": "busy"}` with `Retry-After`, never 5xx (the watchdog scans nginx 5xx lines); timeouts are summarised in one WARNING per minute.
- **Password check.** `backend/auth/passwords.py` `verify_password` returns False for an empty or invalid hash, so `/login` and `/auth/mfa/disable` return the usual 401 for Apple and Google accounts instead of a 500.
- **Watchdog.** `_HTTP_4XX_QUERY` excludes `/api/explorer/` and `/api/auth/apple-web/` so expected 404 and 429 there cannot trip the 4xx anomaly.

## Message threads and message delete (task 20261001-message-threads)

Two capabilities behind two DB flags, `threads` and `message_delete` (both off by default; only the owner flips them). Tunables live in `api/config/chat.json` sections `threads` and `message_delete` (`backend/interactions/threads_config.py`, every key required, validated at startup).

### Message delete (flag `message_delete`)

- **Routes** (`routes/messages_delete.py`, plain `def`): `DELETE /groups/{user_id}/{group_id}/messages/{message_id}` and `POST .../restore`. - **Soft delete and undo.** `deleted_at`/`deleted_by` are set at once and every reader hides the row. `undo_seconds` (10) governs restore only; text and the S3 object are kept.
- **Evidence retention.** `reports._resolve_message` has no `deleted_at` filter, so a report filed after the delete still captures the text. The sweeper (`message_delete.purge_once`, a thin `async def` job every 15 minutes, work in `run_in_executor`, runs even while the flag is off) purges a row only after `evidence_retention_days` (30) and only when no `content_reports` row for it is `open`: it clears the text and attachment columns and `threads.root_preview`, and queues the S3 key in `pending_s3_deletes` only when the key is under the author's own `attachments/<author_id>/` prefix and no other `messages` or `thread_messages` row uses it. - **Rate limits** use `limiter.shared_limit(..., scope=<fixed name>, key_func=<per user>)`. slowapi buckets by URL path unless a shared scope is given, so a per-user limit on a path with an id parameter needs a fixed scope or each id gets its own bucket (this was fixed here and in the Explorer owner routes).

- **Data.** `threads`, `thread_messages`, `thread_followers` (DDL module `threads`, see `api/schema_tree.md`). Thread messages are in their own table, never in `messages`, so no legacy reader needs a filter. One thread per root message (partial unique index), groups only, no nesting, no close or delete (a thread dies with its group). A deleted root leaves the thread alive with `root_deleted: true` and no preview.
- **Routes** (`routes/threads.py`, plain `def`, `group_info.py` untouched): `POST /groups/{user_id}/{group_id}/threads`, `GET .../threads`, `GET .../threads/{thread_id}/messages`, `PUT .../threads/{thread_id}` (see the API overview). Logic is in `backend/interactions/threads.py` (`ThreadsManager`).

It has `type` and neither `from_user` nor `text`, so build 78 and the previous web bundle ignore it.
- **Push.** Followers only, offline only, not blocked, not the sender, not group-muted (mute lookup fails open, like `send_msg`). Data `{action:'thread_message', group_id, thread_id}`, identifiers only.
- **Registrations** (`backend/threads_wiring.py`, one import line in `backend/registrations.py` `load_all`): report resolver and moderation remover for content type `thread_message` (id is `thread_messages._id`; unknown id is `404` and stores nothing; no `deleted_at` filter; the remover hard-deletes the row and queues its author-owned, unreferenced key in the outbox) and a `group_delete` collector for thread attachment keys (keys also used outside the group are kept). ## Join requests (task 20261001-explorer-join-requests)

<!-- JRQ (20261001-explorer-join-requests) -->
A signed-in person asks to join a group from its published Explorer listing and the group's owner approves or denies. It is a second path to group membership next to invite links, and it never creates or reads an invite row or token. Flags are DB rows: `join_requests` (the whole feature) and `join_request_push` (owner and requester pushes), both off by default; tunables are in `api/config/explorer.json` section `join_requests` (`backend/interactions/join_requests_config.py`, every key required, validated at startup).

- **Data.** `group_join_requests` (DDL module `join_requests`, see `api/schema_tree.md`): status `pending|approved|denied|withdrawn|expired`, optional `note`, `block_reapply`, `decided_at/by`, `owner_notified_at`. One PENDING row per (group, applicant) through a partial unique index. The row dies with its group or applicant (FK cascade). It has no FK to `group_listings`.
- **Approver (decision J4).** The owner only: `groups.creator_id = caller` AND the caller is a current member AND not suspended (`join_requests.approver_ok`). `GroupInviteHandler.is_manager` is not reused (it checks the creator only, and `leave_group` never clears `creator_id`). An ownerless group, or one whose owner left, accepts and approves nothing.
- **Routes** (`routes/join_requests.py`, router `/join-requests`, all plain `def`; behaviour in `backend/interactions/join_requests.py`, `JoinRequestsManager`). The flag is evaluated for the caller on every route and off is the uniform 404. Create also needs `explorer_browse` on, the LISTING OWNER inside the flag (a request an owner cannot see is never created), `listings.listing_requestable(cur, public_id)` (published, owner present, accepting, not full; JRQ never re-implements those conditions) and `require_current_terms`. The owner routes need only the caller's flag plus the approver check, so an owner can still clear the queue or switch intake off during a browse rollback.
- **Uniform answers.** Everything that could be an oracle is the same `404 not_found` (flag off, unknown or non-requestable listing, non-approver, request of another group) or the same generic `403 cannot_request` (blocked either direction with any member, cooldown, `block_reapply`, pending caps, daily cap, minimum account age, suspended applicant). `already_member` is answered only to the member.
- **Approve is ONE transaction.** `groups` row `FOR UPDATE` first (the order invite redeem and `leave_group` use), then the request row `FOR UPDATE`, never the reverse. Under both locks: approver re-check, request still pending (already approved is an idempotent 200, deny after approve is 409 `not_pending`), applicant exists and is not suspended, `GroupInviteHandler.existing_outcome` (already a member: marked approved, nothing appended), `redeem_precheck` (member cap and blocks) BEFORE `apply`. `group_full` answers 409 and the request STAYS pending; a block or suspended applicant sets the request to `expired` and answers 409 `no_longer_available`. The member append is `GroupInviteHandler.apply`, the same guarded UPDATE as invite redeem.
- **Bounded waits.** Every transaction that can wait on a lock first arms `lock_timeout` from `join_requests.lock_timeout_ms` (`set_config(..., true)`, the `SET LOCAL` equivalent) and catches SQLSTATE 55P03 around its own raw `cur.execute` calls, before any `DBManager` helper can log `DB_WRITE_FAILURE`. It rolls back and answers 409 `busy` with one INFO line and no ERROR. This keeps a route from holding one of the shared 40 threadpool tokens longer than `lock_timeout_ms`.
- **Create** serialises one user's creates with an advisory lock (exact per-user caps), takes the group lock (exact per-group cap) and re-checks requestability under it. A repeat returns the existing pending request without using a cap.
- **Deny, undo, withdraw** are conditional `UPDATE ... WHERE status = 'pending'`. Deny starts the cooldown (`cooldown_days`) and may set `block_reapply`; the applicant is never notified. Undo is allowed only for the decider, within `undo_deny_seconds` on the server clock, and fails with 409 `not_undoable` if the applicant already asked again.
- **Accepting switch.** `PUT /join-requests/{user_id}/groups/{group_id}/accepting` writes ONLY through `listings.set_accepting_requests` (LST owns the column) and reads through `listings.get_accepting_requests`; the group must have a listing (else the uniform 404). It does not require `explorer_browse` and leaves pending requests untouched.
- **Privacy.** The owner list carries `applicant_user_id` (needed by Report and Block) to the approver only. Notes are visible only to the owner. Notes, usernames and applicant ids never appear in logs, push text or audit lines; `JOIN_REQUEST_AUDIT` lines carry request, group and (owner actions) actor ids only. The requester sees the group's identity only after approval; the title shown to a requester is the listing's own snapshot.
- **Limits.** Per-user and per-IP limits use `shared_limit` with FIXED scopes (`jrq_create`, `jrq_create_ip`, `jrq_withdraw`, `jrq_mine`, `jrq_owner_read`, `jrq_decide`, `jrq_accepting`), values from `rate_limits`.
- **Lifecycle** (`backend/join_requests_wiring.py`, one import line in `backend/registrations.py` `load_all`): `member_leave` (the leaver is `creator_id`: pending rows expire inside the locked leave transaction), `user_delete` (pending rows of groups the deleted account created expire; its own requests cascade) and `listing_hidden` (`fn(cur, group_id, reason)`: pending rows for the group expire). Group deletion relies on the FK cascade through both deletion paths. `listings` never imports this module.
- **Sweeper** (`join_request_sweeper.py`, thin `async def` job every 10 minutes, work in `run_in_executor`, batches use `FOR UPDATE SKIP LOCKED` and never take a group lock): expires pending rows older than `pending_expiry_days` and pending rows of ownerless groups, deletes decided rows older than `max(retention_days, cooldown_days)`; a denied row with `block_reapply` is kept with its note cleared so the owner's decision does not lapse. It runs even while the flag is off. One INFO line with counts, or one WARNING when a pass failed. It also feeds the `pending_join_requests` gauge of the hourly `FEATURE_SUMMARY` line.
- **Push** (`join_request_notifier.py`, modeled on `announcement_notifier.py`): post-commit `BackgroundTask`, gated by `join_request_push` evaluated for the OWNER. One owner push per group per `notify_window_minutes` (atomic claim on `owner_notified_at`, serialised per group by an advisory lock, taken only after every eligibility check passed). Mute respected (lookup fails open), generic copy, payload `{action: 'join_request', group_id}`, per-recipient isolation, never raises. The requester gets one push when an approval appended them.
- **Known limits.** `users` has no creation timestamp, so `min_account_age_hours` (shipped as 0 = off) uses `terms_accepted_at` as a proxy when set above zero. Groups with no listing are not covered by the PUT /groups owner guard (contract decision D7); a direct member-list edit that adds a pending applicant makes the later approve mark the request approved without appending.

Audit table (`affiliate_payout_audit`) is append-only and value-free. Create/update/delete/reveal each email the account owner (never with values).
- **Retention.** Daily job hard-deletes details inactive for `retention_inactive_days` or whose owner has no active creator code/user; audit rows are kept. Backups keep old ciphertext until they age out.
- **Out of scope / note for the owner.** Tax reporting (W-9/1099) and breach-notification duties for holding bank details are not handled here.
