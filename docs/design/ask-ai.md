# Ask AI (single built-in AI, no user-created agents)

Task 20261106-remove-agents-ask-ai. Users no longer create, rename, disable or delete "agents". Every AI interaction (chat, session summaries, scheduled devotions) uses one server-owned default AI, shown to users as **Ask AI**.

The behaviour sits behind the `ask_ai_default_agent` feature flag, **off by default**. With the flag off every client keeps the previous agents UI and `/agent/...` routes unchanged. Flip the flag only after the merge script below has been run for the target database.

## What users see (flag on)

| Where | Behaviour |
|---|---|
| Messages (web, iOS, iPad dock) | The former "Agents" section is titled **Ask AI** and lists the user's separate AI chats (title and relative last activity, most recent first) with a **New AI chat** action. Opening a row resumes that chat with its history. |
| Empty / error states | "No AI chats yet." with a "Start a chat" action; "Couldn't load your chats." with Retry; "Couldn't refresh. Showing saved chats." when a refresh fails but a saved list exists. |
| Account | The Agents card, "New Agent", rename, enable/disable, delete and the event agent picker are gone. An **AI assistant** card says Ask AI is built in and links to Messages. "New scheduled devotion" is always available (no "needs an agent" gate). |
| Scheduled devotions | Same schedule and times as before, generated by the default AI. The push title is the fixed string "Scheduled Devotion" (never an agent name) and the body is "Your scheduled devotion is ready. Check your notes." The push data still carries `heartbeat_id` and `agent_id` (the canonical id) so older clients can deep-link. |
| Onboarding tour | The AI step reads "Ask AI: chat with your AI study companion anytime from Messages." |

Failure handling follows the 2026-09-05 principles. Endpoints throw (4xx/5xx) instead of fabricating a default list or agent. Clients keep the cached Ask AI chat list when a refresh fails (iOS key `askAiChats:<uid>`, web `askAiChats.<uid>` in localStorage) and only replace it on a proven success. With the flag on, the legacy `agents:<uid>` cache is neither read nor written.

## API

All `/ask-ai` routes return a uniform `404` while the flag is off for the caller (WebSocket closes with `4404`). They resolve the user's canonical agent server-side (`AgentManager.ensure_default_agent`); clients never send or learn an agent id. Every route is scoped to the authenticated user (a path user id that does not match the session is rejected).

| Method | Path | Notes |
|---|---|---|
| GET | `/ask-ai/{user_id}/chats` | The user's Ask AI chats, most recent first |
| POST | `/ask-ai/{user_id}/chats` | New chat. `201`, or `409` `chat_limit` (the per-agent cap, 50 by default, now applies to the user's single default AI) |
| GET | `/ask-ai/{user_id}/messages?chat_id=` | History for one chat |
| DELETE | `/ask-ai/{user_id}/messages/{message_id}` | Delete one message |
| WS | `/ask-ai/ws/{user_id}?chat_id=` | Live chat |
| GET | `/ask-ai/{user_id}/heartbeats` | All of the user's scheduled devotions (user-wide) |
| POST | `/ask-ai/{user_id}/heartbeat` | Create a scheduled devotion (free-tier `agent_events` limit unchanged) |
| DELETE | `/ask-ai/{user_id}/heartbeat/{heartbeat_id}` | Delete one |
| POST | `/ask-ai/{user_id}/heartbeats/{heartbeat_id}/commit` | Fire now |
| POST | `/ask-ai/{user_id}/summarize` | Session summary note |

### Legacy compatibility shims

Older iOS and web builds still call `/agent/{user_id}/{agent_id}/...`. Those routes keep working: ownership (`owns_agent`) is still enforced on every one and a guessed or foreign agent id is `404`, never silently replaced by the default. With the flag on, a legacy id the user owns maps to the canonical agent for chat and heartbeat reads and writes; `GET /agent/{user_id}` lists only the canonical agent; legacy create, rename and delete are non-destructive (no cascade). With the flag off the legacy behaviour is unchanged. The shims are removed only after a minimum-supported-iOS bump.

## Data model and migration

- `agents.is_default BOOLEAN` marks each user's one canonical agent; a partial unique index (`idx_agents_one_default_per_user`) allows at most one per user. Added additively at boot.
- The default AI's prompt is read from `backend/interactions/agent_prompt.txt` at call time with the flag on; the stored `agents.role` is ignored (custom personas are preserved only in the archive).
- Existing agents are merged by the operator-run script `api/scripts/merge_agents_to_default.py` (not a boot DDL module). Per user, in one savepointed transaction it chooses the canonical agent, copies every agent row into `agents_archive`, adopts legacy `chat_id IS NULL` messages into the old agent's default chat, prefixes chats from retired agents with the old agent's name, and re-points `agent_chats`, `agent_messages` and `agent_heartbeats` onto the canonical agent. Heartbeat idempotency-key collisions null the later row's key (no heartbeat is ever deleted); schedules and `last_fired` are untouched, so scheduled devotions fire at the same times exactly once. Counts are verified before and after.
- Old `agents` rows are left in place, unreferenced (deleting one would cascade-delete its dependents). Dropping them is a later cleanup task.
- `--dry-run` (default) runs everything and rolls back, printing counts; `--apply` is refused off the scratch database unless `--backup-confirmed "<label>"` is passed. The audit log is JSON lines with ids and counts only (no content, titles, names or roles). The script has been verified only against a scratch database, never production.
